# บทที่ 1 บทนำ

## 1.1 ความเป็นมาและความสำคัญของปัญหา
การเปลี่ยนแปลงรูปแบบการทำงานในองค์กรสู่ลักษณะยืดหยุ่นและการใช้งานพื้นที่ร่วมกัน ทำให้การบริหารจัดการที่นั่งเข้าออฟฟิศกลายเป็นโจทย์สำคัญทั้งในมิติการจัดสรรทรัพยากร ความเป็นธรรมในการใช้งาน และความถูกต้องของข้อมูลสำหรับการบริหาร โครงการ `co_desk` หรือ codesk จึงถูกกำหนดขึ้นในฐานะระบบเว็บสำหรับจองที่นั่งเข้าออฟฟิศที่ต้องรองรับทั้งการปฏิบัติงานจริงของผู้ใช้และการกำกับดูแลระดับองค์กร โดยเชื่อมโยงการออกแบบระบบกับแนวคิดด้านฐานข้อมูล สิทธิ์การเข้าถึง และการตรวจสอบย้อนกลับข้อมูลอย่างเป็นระบบ

การจัดทำ Short Paper ฉบับนี้มีความสำคัญในเชิงวิชาการและเชิงวิศวกรรมระบบ เนื่องจากเป็นขั้นตอนในการจัดระเบียบปัญหา กำหนดเหตุผลเชิงหลักการ และวางกรอบการดำเนินงานก่อนพัฒนาระบบเต็มรูปแบบ เนื้อหาในบทนำจึงมุ่งอธิบายความจำเป็นของการมีระบบที่สามารถป้องกันการจองซ้อน ควบคุมความจุรายแผนก จัดการสิทธิ์ตามบทบาท และสนับสนุนการรายงานเพื่อการตัดสินใจ โดยยึดมาตรฐานข้อมูลเดียวกันทั้งระบบ ได้แก่ รูปแบบวันที่ `YYYY-MM-DD` และเขตเวลา `Asia/Bangkok`

## 1.2 ปัญหาที่พบในกระบวนการเดิม / Pain Points
กระบวนการจองที่นั่งแบบเดิมมักมีข้อจำกัดจากการกระจายข้อมูลอยู่หลายแหล่งและขาดกติกากลางที่ระบบบังคับใช้จริง ส่งผลให้เกิดปัญหาการจองซ้ำในช่วงเวลาเดียวกัน การบริหารความจุที่นั่งของแต่ละแผนกไม่แม่นยำ และความคลุมเครือในการตีความเวลาและวันที่เมื่อผู้ใช้งานมีรูปแบบการบันทึกไม่ตรงกัน ปัญหาเหล่านี้กระทบต่อการปฏิบัติงานประจำวันโดยตรง และเพิ่มต้นทุนการประสานงานของหน่วยงานที่รับผิดชอบ

อีกประเด็นสำคัญคือการควบคุมสิทธิ์การเข้าถึงข้อมูลและฟังก์ชันยังไม่ละเอียดพอเมื่อเทียบกับบทบาทผู้ใช้จริงในองค์กร หากไม่มีการแยกสิทธิ์อย่างชัดเจนระหว่าง `employee`, `hr` และ `admin` อาจเกิดความเสี่ยงทั้งด้านความถูกต้องของข้อมูลและธรรมาภิบาลข้อมูล นอกจากนี้ องค์กรมักต้องการมุมมองรายงานเพื่อการบริหารอย่างน้อย 5 มุมมองจาก reporting views และต้องมีความสามารถกรองข้อมูลเชิงคอลัมน์เพื่อวิเคราะห์เชิงลึก ซึ่งกระบวนการเดิมไม่รองรับอย่างเป็นระบบ

## 1.3 วัตถุประสงค์ของโครงการ
โครงการนี้มีวัตถุประสงค์เพื่อพัฒนากรอบระบบจองที่นั่งเข้าออฟฟิศที่สอดคล้องกับบริบทการใช้งานจริงขององค์กร โดยเน้นการกำหนดหลักเกณฑ์เชิงระบบให้ชัดเจนตั้งแต่ต้นทาง ได้แก่ การรองรับการจองทั้งแบบทั้งวันและช่วงเวลา การป้องกันการจองซ้อนของผู้ใช้รายเดียวกัน การตรวจสอบความจุรายแผนกในลักษณะ limited และ unlimited และการจัดการกรณีวันหยุดด้วยกลไกแจ้งเตือนพร้อมการยืนยันก่อนบันทึกการจอง

ในเชิงสถาปัตยกรรม วัตถุประสงค์อีกส่วนคือการกำหนดทิศทางพัฒนาให้มีความพร้อมต่อการนำไปใช้งานจริงผ่านสแตกที่กำหนดไว้ ได้แก่ React สำหรับส่วนติดต่อผู้ใช้ ASP.NET Core Web API สำหรับบริการหลังบ้าน และ Supabase PostgreSQL/Auth/RLS สำหรับข้อมูลและการยืนยันตัวตน ทั้งนี้เพื่อให้ระบบสามารถบังคับใช้ RBAC ได้จริงตามบทบาทผู้ใช้ สนับสนุนการรายงานเพื่อการบริหาร และเป็นฐานข้อมูลที่ตรวจสอบย้อนกลับได้สำหรับการตัดสินใจขององค์กร

## 1.4 ขอบเขตของโครงการ (Functional Scope และ Role Scope)
ขอบเขตเชิงฟังก์ชันของโครงการครอบคลุมระบบจองที่นั่ง ปฏิทินการใช้งาน การจัดการฝ่ายงาน การจัดการพนักงาน การจัดการวันหยุด ระบบรายงาน และระบบผู้ใช้/สิทธิ์ โดยระบบจองต้องรองรับการจองทั้งวันหรือช่วงเวลาแบบไม่ละเอียดถึงนาที รองรับการจองข้ามวัน จองย้อนหลัง และจองล่วงหน้า พร้อมกติกาป้องกันการจองซ้ำในช่วงเวลาเดียวกันและกติกาควบคุม over-capacity ตามความจุของแผนก รวมถึงรองรับการจองในวันหยุดโดยต้องแสดงคำเตือนและให้ผู้ใช้ยืนยันก่อนดำเนินการต่อ

ขอบเขตเชิงบทบาทกำหนดให้ `admin` มีสิทธิ์ครอบคลุมทุกเมนูและสามารถสร้างผู้ใช้พร้อมกำหนดบทบาทได้ `hr` มีสิทธิ์จัดการฝ่ายและพนักงาน รวมถึงดูรายงานได้ แต่จองที่นั่งได้เฉพาะของตนเองและเห็นปฏิทินเฉพาะฝ่ายเดียวกัน ส่วน `employee` จองได้เฉพาะของตนเองและเห็นปฏิทินในขอบเขตเดียวกันกับฝ่ายของตน ระบบยืนยันตัวตนใช้ Supabase Auth และใช้แนวทาง RLS เพื่อควบคุมการเข้าถึงข้อมูลในระดับแถว โดยการจัดเก็บและแสดงผลข้อมูลวันเวลาต้องสอดคล้องกับเขตเวลา `Asia/Bangkok` และใช้รูปแบบวันที่ `YYYY-MM-DD` ทั้งระบบ

## 1.5 ประโยชน์ที่คาดว่าจะได้รับ
ผลที่คาดว่าจะได้รับในระดับการดำเนินงานคือองค์กรสามารถบริหารการเข้าใช้ออฟฟิศได้อย่างเป็นระบบ ลดความขัดแย้งจากการจองซ้อน และรักษาวินัยการใช้ทรัพยากรตามความจุของแต่ละแผนกได้อย่างชัดเจน ผู้ใช้งานแต่ละบทบาทสามารถปฏิบัติงานได้ตามสิทธิ์ที่กำหนด ลดความเสี่ยงจากการเข้าถึงข้อมูลเกินขอบเขต และเพิ่มความโปร่งใสในการติดตามการใช้งานพื้นที่ร่วมกัน

ในระดับการบริหารและวิชาการ ระบบช่วยสร้างฐานข้อมูลที่มีมาตรฐานเดียวกันและนำไปวิเคราะห์ได้ต่อเนื่องผ่านรายงานอย่างน้อย 5 มุมมอง ขณะเดียวกันเอกสารบทนำที่จัดทำใน Short Paper นี้จะทำหน้าที่เป็นกรอบอ้างอิงสำหรับบทที่ 2 และบทที่ 3 รวมถึงเป็นพื้นฐานเชิงเหตุผลในการพัฒนาระบบฉบับสมบูรณ์ต่อไปโดยไม่คลาดเคลื่อนจากข้อกำหนดเชิงธุรกิจของโครงการ
