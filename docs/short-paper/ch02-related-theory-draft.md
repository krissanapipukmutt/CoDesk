# บทที่ 2 ทฤษฎีและหลักการที่เกี่ยวข้อง

## 2.1 แนวคิดระบบฐานข้อมูลเชิงสัมพันธ์
ระบบฐานข้อมูลเชิงสัมพันธ์เป็นแนวคิดหลักที่ใช้กับงานที่ต้องการความเป็นระเบียบของข้อมูลและความน่าเชื่อถือในการประมวลผล โดยจัดเก็บข้อมูลเป็นตาราง เชื่อมโยงด้วยคีย์ และสืบค้นด้วย SQL [1] สำหรับโครงการ `co_desk` แนวคิดนี้เหมาะกับลักษณะข้อมูลที่สัมพันธ์กันหลายส่วน เช่น ผู้ใช้ ฝ่ายงาน รายการจอง วันหยุด และข้อมูลรายงาน ซึ่งต้องตรวจสอบย้อนกลับได้และใช้ต่อในการบริหารจริง

เหตุผลที่เลือกแนวทางนี้คือโครงการไม่ได้ต้องการเพียง "บันทึกข้อมูลให้ได้" แต่ต้องการให้ข้อมูลคงความถูกต้องเมื่อมีการใช้งานพร้อมกันและมีเงื่อนไขทางธุรกิจหลายชั้น การใช้โครงสร้างเชิงสัมพันธ์จึงช่วยวางกติกาไว้ที่ชั้นข้อมูลได้ตั้งแต่ต้น และลดความคลาดเคลื่อนจากการตีความข้อมูลไม่ตรงกันในแต่ละส่วนของระบบ [1]

## 2.2 การออกแบบฐานข้อมูลและความถูกต้องของข้อมูล (Constraints, Transactions)
หลักการสำคัญของบทนี้คือการออกแบบฐานข้อมูลให้รองรับกติกาธุรกิจจริง โดยใช้ข้อบังคับข้อมูล เช่น `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK` และ `NOT NULL` เพื่อป้องกันข้อมูลไม่สมบูรณ์หรือขัดเงื่อนไขตั้งแต่ระดับฐานข้อมูล [1] ในบริบทของ `co_desk` ข้อกำหนดเรื่องการจองซ้ำในช่วงเวลาเดียวกัน การควบคุมความจุรายแผนก และการจัดการสถานะการจอง ล้วนต้องพึ่งข้อบังคับเหล่านี้เป็นฐาน

อีกส่วนที่สำคัญคือแนวคิดเรื่องธุรกรรม (transactions) ซึ่งช่วยให้การบันทึกข้อมูลหลายขั้นตอนเกิดขึ้นอย่างปลอดภัยและครบถ้วน โดยเฉพาะกรณีที่มีการใช้งานพร้อมกันจนเสี่ยงต่อ over-capacity หรือข้อมูลจองทับกัน [1] นอกจากนี้ โครงการกำหนดมาตรฐานวันเวลาให้ชัดเจนด้วยรูปแบบ `YYYY-MM-DD` และเขตเวลา `Asia/Bangkok` เพื่อให้การคำนวณช่วงเวลาการจองและการสรุปรายวันใช้เกณฑ์เดียวกันตลอดระบบ [1]

## 2.3 การควบคุมสิทธิ์การเข้าถึงข้อมูล (RBAC, RLS)
แนวคิด RBAC ช่วยให้การกำหนดสิทธิ์สอดคล้องกับบทบาทของผู้ใช้ในองค์กร โดยลดการกระจายสิทธิ์แบบเฉพาะบุคคลที่ดูแลยากในระยะยาว [4] โครงการนี้จึงกำหนดบทบาทหลักเป็น `employee`, `hr` และ `admin` แล้วผูกสิทธิ์การใช้งานกับแต่ละบทบาทอย่างชัดเจน เช่น สิทธิ์การจอง การจัดการข้อมูลพนักงาน และสิทธิ์การดูรายงาน

อย่างไรก็ตาม การควบคุมสิทธิ์ที่ชั้นเมนูเพียงอย่างเดียวไม่เพียงพอสำหรับข้อมูลที่มีความอ่อนไหว โครงการจึงใช้ Supabase Auth ร่วมกับ Row-Level Security (RLS) เพื่อบังคับนโยบายการเข้าถึงที่ชั้นฐานข้อมูลด้วย [2][3] วิธีนี้ทำให้เงื่อนไขการเห็นข้อมูลและการแก้ไขข้อมูลสอดคล้องกับตัวตนผู้ใช้ที่ล็อกอินจริง และช่วยลดความเสี่ยงจากการเข้าถึงข้อมูลเกินสิทธิ์

## 2.4 เทคโนโลยีที่ใช้พัฒนาระบบ (React, .NET, Supabase, FullCalendar, TanStack Table ฯลฯ)
ในด้านเทคโนโลยี โครงการเลือก React เป็นโครงสร้างส่วนติดต่อผู้ใช้ และใช้ TypeScript เพื่อควบคุมชนิดข้อมูลให้ชัดเจนขึ้นในงานพัฒนาหน้าจอ [5] ส่วนบริการหลังบ้านใช้ ASP.NET Core Web API เพื่อจัดระเบียบตรรกะธุรกิจและแยกหน้าที่กับชั้นนำเสนออย่างเป็นระบบ [6] แนวทางนี้ช่วยให้การพัฒนาและบำรุงรักษาในระยะถัดไปทำได้ง่ายขึ้น

ด้านข้อมูลและการยืนยันตัวตนใช้ Supabase PostgreSQL/Auth/RLS เพื่อให้โครงสร้างข้อมูลและสิทธิ์ทำงานร่วมกันตั้งแต่ระดับแพลตฟอร์ม [2][3] ขณะที่เครื่องมือเฉพาะงานอย่าง FullCalendar, TanStack Table และ Recharts ถูกเลือกเพื่อรองรับงานปฏิทิน การกรองรายงานเชิงคอลัมน์ และการสรุปผลในรูปแบบภาพตาม requirement ฝั่งผู้ใช้งานและผู้บริหาร โดยรวมแล้วเทคโนโลยีที่เลือกไม่ได้เน้นความซับซ้อนเกินจำเป็น แต่เน้นความสอดคล้องกับโจทย์ธุรกิจของระบบจองที่นั่ง

## 2.5 การเปรียบเทียบเครื่องมือฐานข้อมูลที่ใช้กับ Oracle
แม้ฐานข้อมูลที่ใช้จริงในโครงการนี้ไม่ใช่ Oracle แต่เป็น Supabase PostgreSQL การเปรียบเทียบยังมีความจำเป็นเพื่อชี้แจงเหตุผลการเลือกเครื่องมือ โครงการใช้ Supabase PostgreSQL สำหรับจัดเก็บข้อมูลเชิงธุรกรรม ใช้ SQL/constraints/views รองรับรายงาน และใช้ Auth/RLS เพื่อควบคุมสิทธิ์ระดับข้อมูล [2][3] ซึ่งสอดคล้องกับ requirement ของระบบนี้โดยตรง

ในมุมความเหมือน Oracle และ PostgreSQL ต่างเป็น RDBMS ที่รองรับแนวคิดหลักร่วมกัน เช่น SQL, constraints, views และ transactions [1][7] ส่วนความต่างอยู่ที่ระบบนิเวศและแนวทางใช้งาน โดย Supabase เน้นการเป็น managed platform ที่เชื่อมฐานข้อมูลกับงานเว็บแอปสมัยใหม่ได้เร็ว รวมถึงการผนวก auth และ RLS ในรูปแบบที่ใช้งานร่วมกับแอปได้ทันที [2][3] ขณะที่ Oracle มี ecosystem สำหรับองค์กรขนาดใหญ่และมีโครงสร้างด้าน licensing/platform เชิงพาณิชย์ที่แตกต่างออกไป [8] ดังนั้น การเลือก Supabase PostgreSQL จึงเป็นการเลือกที่เหมาะกับขอบเขตงานและทรัพยากรของโครงการในระยะนี้

## 2.6 แนวคิดการสร้างผู้ใช้โดยผู้ดูแลระบบอย่างปลอดภัย
เมื่อระบบกำหนดให้ `admin` สามารถสร้างผู้ใช้ใหม่ใน Supabase Auth ผ่านหน้าเว็บได้ การออกแบบจำเป็นต้องยึดหลัก secure administrative user provisioning โดยแยกสิทธิ์เชิงปฏิบัติการออกจากส่วนติดต่อผู้ใช้อย่างชัดเจน กล่าวคือ frontend ทำหน้าที่ส่งคำขอผ่าน endpoint ของ backend เท่านั้น และ backend เป็นชั้นที่ตรวจสอบสิทธิ์ผู้เรียกก่อนดำเนินการสร้างผู้ใช้ใน `auth.users` [3][4][6] แนวคิดนี้ช่วยให้การกำกับสิทธิ์สอดคล้องกับ RBAC และลดความเสี่ยงจากการให้ client เข้าถึงความสามารถระดับผู้ดูแลโดยตรง

ในมุมความปลอดภัยเชิงระบบ หลัก least privilege และ secret management มีบทบาทสำคัญ เพราะการเรียก Supabase Admin API ต้องอาศัยคีย์ที่มีสิทธิ์สูง จึงต้องจำกัดการถือครองคีย์ไว้ฝั่ง server เท่านั้น และห้ามเผยแพร่คีย์ดังกล่าวใน frontend หรือสภาพแวดล้อมที่ผู้ใช้เข้าถึงได้ [2][3] นอกจากนี้ กระบวนการ provisioning ควรผูกกับการตรวจสอบความถูกต้องของข้อมูลประกอบ เช่น email, role, department และสถานะผู้ใช้ เพื่อป้องกันการสร้างบัญชีที่ไม่สอดคล้องกับนโยบายข้อมูลขององค์กร

## 2.7 สรุปการนำทฤษฎี/หลักการมาใช้ในโครงการ
จากการทบทวนทฤษฎีและเทคโนโลยีที่เกี่ยวข้อง สามารถสรุปได้ว่าโครงการ `co_desk` ใช้แนวคิดฐานข้อมูลเชิงสัมพันธ์เป็นแกนกลางของความถูกต้องข้อมูล ใช้ constraints และธุรกรรมเพื่อรองรับกติกาการจองจริง ใช้ RBAC และ RLS เพื่อควบคุมสิทธิ์ตามบทบาท และเลือกเทคโนโลยีที่ตอบโจทย์การพัฒนาเว็บแอปในบริบทองค์กร [1][3][4]

ในภาพรวม บทนี้สนับสนุนว่าการเลือก Supabase PostgreSQL แทน Oracle ไม่ได้ลดคุณภาพเชิงหลักการของระบบฐานข้อมูล แต่เป็นการเลือกเครื่องมือที่เหมาะกับลักษณะงาน ข้อกำหนดด้านสิทธิ์ และรูปแบบการพัฒนาในโครงการนี้มากกว่า [2][7][8] โดยเฉพาะโจทย์การสร้างผู้ใช้ระดับผู้ดูแลที่ต้องคงหลัก server-side control, RBAC และการจัดการความลับของระบบอย่างเคร่งครัด
